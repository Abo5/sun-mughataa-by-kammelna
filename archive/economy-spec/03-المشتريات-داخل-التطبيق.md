# ٠٣ — المشتريات داخل التطبيق (IAP)

[↩ الفهرس](README.md)

> `IAPController` — **١١١ دالّة، ~٣٦ كيلوبايت**. هو مسار المال الحقيقي، ولم يكن مؤرشفًا
> إلّا بإشارات عابرة. الفصلان [٠١](01-الاقتصاد-الكامل.md) و[٠٢](02-تدقيق-ARM64.md)
> يغطّيان الكتالوج والعملة الداخلية؛ هذا يغطّي **الشراء بمال حقيقي**.
> ⇒ ⭐ **وتفكيك المحرّك نفسه (آلة حالة التهيئة · مَن يستدعي `confirm` · مرشِّحات `ProductStore`)
> في [٠٥ — محرّك IAP مفكوكًا](05-محرّك-IAP-مفكوكًا.md)**، وفيه تصحيحات لهذا الفصل.

## ⭐ خمس نتائج تسبق كل شيء

1. **ثلاث واجهات متجر خلفية في نفس الثنائي**: Apple StoreKit · Google Play Billing · Huawei IAP
   — وكلّها تصبّ في مسار تحقّق **خادميّ واحد**.
2. **التحقّق كلّه على الخادم** ✅ — العميل لا يمنح أي شيء قبل ردّ الخادم.
3. 🛑 ~~**الخادم يردّ بحقل `Payload`** يُفكّ بـ`JsonMapper.ToObject`~~ — **خطأ، انظر التصحيح في
   [§٣](#-تصحيح--extractpayload-ليست-ردّ-الخادم)**: الخادم يردّ `long`/`bool`، و`ExtractPayload`
   تفكّ **غلاف إيصال Unity المحلّيّ قبل الإرسال**. لكن الخلاصة تبقى: **ما يُمنَح يقرّره الخادم**،
   لا جدول في العميل.
4. **٣٠ قناة بيع** (`SalesChannel`) — كثير منها إقليميّ سعوديّ (Jarir، Obeikan، STC Pay، Urway).
5. **الاشتراكات لها مسار أهليّة عرض تمهيديّ منفصل** يعتمد StoreKit2 وذاكرة محلّية.

public class ProductViewModel {

    string name;      // 0x18

> **المنح المجّانية تمرّ بنفس خطّ أنابيب الشراء** بقناة مختلفة — تصميم نظيف يوحّد المحاسبة.
> ⚠️ **احتفظ بالترقيم حرفيًّا** إن أردت توافقًا مع أي بيانات قائمة.

## ٣. ⭐⭐ مسار الشراء والتحقّق

```
InitiateBuyingProduct @0x508B870 / @0x508B958
        ↓
   BuyProduct @0x508BB24  (2,428B — أكبر دالّة في الصنف)
        ↓ (المتجر الأصليّ ينجز الدفع)
   OnPurchasePending @0x508B03C (712B)
        ↓
   ValidateReceipt @0x508CD30 (628B)     ← 🛑 سجلٌّ فقط، لا تحقّق (٠٥ §٢.٢)
        │  Debug.Log("___# Receipt received: for = " + … + "  and transactionID = " + …)
        ↓
   SubmitReceipt @0x508CFA4 (1,116B)        ← POST إلى الخادم
        ↓
   ┌── OnServerSuccess @0x508D4BC ──→ ExtractPayload @0x508D400
   │                                     JsonMapper.ToObject(json)["Payload"]
   │                                     ProductStore.GetListing(...)
   │                                        ↓
   │                                  OnPurchaseCompleted @0x508D5D4 (660B)
   └── OnServerError   @0x508D868 ──→ ⭐ confirm() إن كان الخطأ AlreadyProcessed=7002
                                       + TrackerLibrary.DevPurchaseServerError
                                       + Tracker.DesignEvent
                                       + OnPurchaseFailed @0x508B594  (يتجاهل message 🚩)
```

### 🛑 تصحيح — `ExtractPayload` ليست ردّ الخادم

> **كنتُ مخطئًا هنا.** `ExtractPayload` @`0x508D400` لها **مستدعٍ واحد فقط** @`0x508D2D0`،
> وهو **داخل `SubmitReceipt`** (`0x508CFA4`–`0x508D400`) — أي **قبل إرسال الطلب**.
> وظيفتها **فكّ غلاف إيصال Unity المحلّي** لاستخراج الإيصال الأصليّ:
> ```csharp
> return JsonMapper.ToObject(receipt)["Payload"].ToString();   // غلاف Unity: {Store, TransactionID, Payload}
> ```

### ✅ ما يردّه الخادم فعلًا

| الطلب | نوع الردّ |
|---|---|
| `BuyConsumableProductRequest : JsonWebRequest<IapReceiptModel, long>` | **`long`** = معرّف المستلِم |
| `BuySubscriptionRequest : JsonWebRequest<IapReceiptModel, bool>` | **`bool`** |

**لا `Payload` ولا وصف للمنح في الردّ.** المنح يقع كلّه على الخادم، والعميل يُزامَن عبر SFS:
`BuyConsumableProductRequest.OnSuccess` @`0x5279598` ⇒ `SFS.SendRefreshInventory()` ·
`BuySubscriptionRequest.OnSuccess` @`0x52796E4` ⇒ `SFS.SendRefreshStatus()` ✅.

والنوافذ تُغذَّى من **الكتالوج المحلّي** (`product.coins` · `product.days`) لا من ردّ الخادم.

> ⭐ **الاستنتاج التصميميّ يبقى صحيحًا بل يزداد قوّة**: **العميل لا يمنح شيئًا.**
> لكن آليّة النقل هي «الخادم يمنح ← SFS يزامن ← العميل يعرض رقمًا من الكتالوج»،
> لا «الخادم يردّ بحمولة تصف المنح».

`OnPurchaseCompleted`:
> ```csharp
> PopupWindow.DismissMessage();
> var p = listing.getProduct();
> if (p.IsSubscription) ShowUpdatedSubscriptionPopup(...);   // @0x508D978
> else if (p.IsCoins)   ShowUpdatedAcesPopup(...);           // @0x508DD24
> ```
> ⇒ **النافذة تُعرض بعد تأكيد الخادم لا قبله.** انسخ هذا الترتيب حرفيًّا —
> عكسُه هو الخطأ الكلاسيكيّ الذي يسمح بمنح وهميّ.

## ٧. ⭐ قائمة إعادة البناء

1. **لا تمنح شيئًا قبل ردّ الخادم.** العميل يرسل إيصالًا ويعرض ما يقوله `Payload`.
2. **افصل المنتج عن قوائم بيعه** (`ProductViewModel` ← `List<ProductListingModel>`).
3. **وحّد المنح المجّانية في نفس خطّ الشراء** بقناة `SalesChannel` مختلفة.
4. **وقّع عروض Apple على خادمك** — لا تضع مفتاح التوقيع في العميل أبدًا.
5. **اعرض سعر المتجر المُحلَّى**، وتتبّع بسعر الكتالوج.
6. اجعل `isHidden` تصفية عرض لا تصفية تحميل.
7. اعرض النافذة بعد `OnPurchaseCompleted` لا عند نجاح الدفع الأصليّ.

## ٧.٦ ⭐⭐ جسم طلب الإيصال — الحقول بالضبط ✅

```csharp
class IapReceiptModel {              // TypeDefIndex 4063
    SalesChannel  Channel;        // 0x10
    string        Receipt;        // 0x18
    string        TransactionID;  // 0x20
    long?         RecipientID;    // 0x28
    string        GiftMessage;    // 0x38
}
```
**هذا جسم POST كاملًا — لا حقول أخرى.**

```csharp
// SubmitReceipt(PendingOrder, Action) @0x508CFA4
string receipt = order.Info.Apple?.jwsRepresentation            // ⭐⭐ StoreKit 2 JWS كما هو
              ?? ExtractPayload(order.Info.Receipt);            // وإلّا فُكّ غلاف Unity
SubmitReceipt(ProductStore.GetListing(store, listingId), receipt, order.Info.TransactionID, …);

// SubmitReceipt(listing, receipt, txId, confirm, track) @0x5089EC0
if (listing.isConsumable) KammelnaRequests.BuyConsumable(channel, receipt, txId, _giftInfo, …);
else { _giftInfo = null;  KammelnaRequests.BuySubscription(channel, receipt, txId, …); }   // ⭐ الاشتراكات لا تُهدى
```

> ⭐⭐ **على Apple يُرسَل `jwsRepresentation` (StoreKit 2) كما هو** — لا إيصال base64 التقليديّ،
> ولا يمرّ بـ`ExtractPayload`. أهمّ نقطة توافق في المسار كلّه.
> ✅ **مسار هواوي يستدعي نفس الدالّة** (نداء ذيليّ من `0x5089C70`) — لا `SubmitReceipt` منفصل.

### ⭐⭐ ترتيب `OnServerSuccess` @`0x508D4BC` — انسخه حرفيًّا
```csharp
confirm();                       // ← تأكيد/استهلاك معاملة المتجر بعد موافقة الخادم فقط
KLogger.Log("Purchased item : " + listing.listingId + " successfully");
trackPurchase();
OnPurchaseCompleted(listing, (g != null && g.RecipientId == recipientId) ? g : null);   // حارس مطابقة المستلِم
```
> **العميل لا يُنهي معاملة المتجر قبل أن يقبل الخادم الإيصال.** عكسُه يفقد المال عند فشل الشبكة.

## ٧.٧ الثلاثيّة `OnPurchaseFailed` — فُرِّقت ✅

| العنوان | التوقيع | المصدر |
|---|---|---|
| `0x508B308` | `(FailedOrder order)` | مُسجَّلة على **Unity `StoreController`** |
| `0x508B6FC` | `(int responseCode)` | ردّ **GooglePlayBillingManager** حصرًا (لا هواوي — لها `OnHuaweiPurchaseFailed` @`0x508A118`) |
| **`0x508B594`** | `(ProductListingModel, string error)` | **الوجهة الموحّدة** التي تنتهي إليها الاثنتان و`OnServerError` |

```csharp
// 0x508B594
PopupWindow.DismissMessage();
if (error != PurchaseFailureReason.UserCancelled.ToString())     // ⭐ صمت تامّ عند الإلغاء
    OnIAPPurchaseFailed?.Invoke(listing, error);
Debug.LogError("___# OnPurchaseFailed: …");
```
> ⭐ **«إلغاء المستخدم ليس خطأً»** — لا تُبلّغ المشتركين، لكن سجّله.
> جدول تحويل Google: `1→UserCancelled` · `4→ProductUnavailable` · `3→PurchasingUnavailable` · غيرها `→Unknown`.

## ٧.٨ ⛔ مسار هواوي **ميّت على iOS** — نفي مُثبَت ✅

| الدالّة | البوّابة | على iOS |
|---|---|---|
| `InitializeStoreKitManager` | `if (KUtil.GetPlatform() != IOS) return;` | **حيّة** |
| `InitializeGooglePlayBillingManager` | `if (Application.platform != Android) return;` | **ميّتة** |
| `InitializeHuaweiIapManager` | `!= Android` **ثم** `GetPlatform() != Huawei` | **ميّتة مرّتين** |

ولمّا كان `KUtil.GetPlatform()` حرفيًّا `mov w0,#2; ret` ([`voice-spec`](../voice-spec/README.md))
فالشرطان ثابتا الكذب وقت الترجمة ⇒ **`m_HuaweiIapManager` يبقى `null` طوال عمر التطبيق**،
وكل دوالّ هواوي بصفر مستدعٍ فعليّ.
> ⇒ **احذف فرع هواوي كاملًا عند إعادة البناء لـiOS.**

## ٧.٩ `BuildProductDefinitions` — مرشِّح القنوات ✅

```csharp
ProductStore.AllRecurringSubscriptions(store).ForEach(p => p.listings.Where(filter)
    .ForEach(l => defs.Add(new ProductDefinition(l.listingId, ProductType.Subscription))));
ProductStore.AllConsumables(store).ForEach(… ProductType.Consumable …);
```
**المرشِّح** (نسختان **متطابقتان بايتًا ببايت** @`0x508EB40` و`0x508EBB0`):
```asm
w8 = channelId - 9 ;  return (w8 < 13) && ((0x1D19 >> w8) & 1)
```
⇒ القنوات المقبولة: `Ios(9) · GooglePlay(12) · GooglePlayRecurring(13) · IosRecurring(17) ·
IosRecurringFreeTrial(19) · IosGameStore(20) · GooglePlayGameStore(21)`

> 🛑 **`GooglePlayRecurringFreeTrial(18)` مستثناة** بينما نظيرها على iOS (`19`) مشمولة
> ⇒ يبدو **خللًا في الأصل لا قرارًا**. **أدرِجها في نسختك.**
> ✅ `storeSpecificId` لا يُمرَّر ⇒ **SKU الخادم = SKU المتجر**.

## ٧.١٠ العروض الموقَّعة 🔒

```csharp
class Offer { int Id; string StoreOfferId; OfferType Type; Decimal Price; }
enum OfferType { Introductory = 1, Promotional = 2, OfferCode = 3, WinBack = 4 }
```
`InitiateBuyingOffer` @`0x508C4A0` يجد القائمة عبر `listing.Offers` ثم ينادي `BuyProduct`.
والتكملة `<BuyProduct>b__0` @`0x508F488`:
```csharp
m_StoreKitManager.BuyProduct(listing.listingId, LocalUser.GetDbId(),
                             JsonConvert.SerializeObject(response.Model));  // AppStorePromotionalOffer
```
`AppStorePromotionalOffer` يحمل `OfferIdentifier` · `Signature` · `Nonce` · `Timestamp` · `KeyIdentifier`.

> 🔒 **هذه القيم تأتي من الخادم وقت التشغيل** عبر `GET api/OfferPurchase/GetAppStoreOfferSignature`،
> و**مفتاح التوقيع الخاص غير موجود في الثنائي إطلاقًا** — تأكيد بالكود لا بالاستنتاج ✅.
> افعل مثله في نسختك.

`PresentPlatformCodeRedeemSheet` @`0x508C7A0`: على iOS ⇒ `AppleStoreExtendedPurchase.PresentCodeRedemptionSheet()`،
وإلّا `ArgumentException("Trying to present code redemption sheet for unsupported platform")`.

## ٨. ما لم يُحسم 🟡

1. ~~`BuyProduct`~~ · ~~جسم `SubmitReceipt`~~ · ~~مسار هواوي~~ · ~~`OnPurchaseFailed` ×٣~~ ·
   ~~`TrackPurchase`~~ · ~~`BuildProductDefinitions`~~ — ✅ **كلّها حُسمت**، انظر §٧.٥–٧.١١.
2. ~~**الوجهة النهائية للتتبّع**: `DataTracking` يستعمل نمط الاستراتيجية بثلاث وجهات متوازية —
   `FirebaseAnalyticsStrategy` (7,656B) · `GameAnalyticsStrategy` (1,856B) · `AdjustStrategy` (1,264B)…
   ويبقى مفكوكًا كيف يُوزَّع الحدث على الاستراتيجيات الثلاث.~~
   🛑 **خطأ، صُحّح في [`data-spec/04`](../data-spec/04-طبقة-التتبّع.md)**: الأصناف الثلاثة موجودة
   في الثنائي، لكن **`GameAnalyticsStrategy` وحدها تُنشأ** — `Tracker.Initialize` @`0x519240C`
   (٢٥٢ بايتًا، مفكوكة كاملةً) يُنشئ واحدة ويضيفها، و`.ctor` كلٍّ من `FirebaseAnalyticsStrategy`
   @`0x51A6A90` و`AdjustStrategy` @`0x51A47C0` له **صفر مستدعٍ** في كلّ `__TEXT` (`bl`+`b`).
   ⇒ **لا توزيع على ثلاث وجهات**: الحلقة تمرّ على قائمة ذات عنصر واحد، والوجهة الحيّة الوحيدة
   **GameAnalytics**؛ وFirebase لا يتلقّى إلّا سِمات ملف اللاعب و`Crashlytics.SetUserId`.
3. ~~`ProductStore.GetConsumableVersion` @`0x509247C` (636B) — كيف تُطابق نسخة مستهلَكة بمتكرّرة.~~
   ✅ **حُسم في [٠٥ §٣.٢](05-محرّك-IAP-مفكوكًا.md)**: `if (l.isConsumable) return l;` ثم
   `Products.FirstOrDefault(p => p.listings.Contains(l))` ثم `product.listings.FirstOrDefault(l => l.isConsumable)`.
   🛑 **وتصحيح للتوقيع في §٧.٥ أعلاه**: هي **دالّة مثيل تأخذ `ProductListingModel` نفسه**
   (`store.GetConsumableVersion(listing)`) لا `(store, listingId)`.
   🚩 والمطابقة بـ`List<ProductListingModel>.Contains` @`0x3464A18` = **هويّة مرجعيّة**
   (الصنف لا يُلغي `Equals`) ⇒ إعادة تحميل الكتالوج بين الاختيار والشراء تُفشل الإهداء. **طابِق بـ`listingId`.**
4. ~~`ValidateReceipt` @`0x508CD30` و`OnPurchasePending` @`0x508B03C` — متى يُستدعى `confirm` بالضبط.~~
   ✅ **حُسم في [٠٥ §٢](05-محرّك-IAP-مفكوكًا.md)** — وهذه أهمّ نتيجة ماليّة في الأرشيف:
   * `confirm` = **`() => m_StoreController.ConfirmPurchase(order)`** (`b__0` @`0x508F2D0`)،
     يُبنى في `OnPurchasePending` ويُمرَّر يدًا بيد.
   * `OnPurchasePending` **لا يتحقّق فورًا**، بل `ReadyState.CallWhenReady(() => ValidateReceipt(order, confirm))`
     (`OneShotEvent` @`0x4EE6F58`) ⇒ الإيصالات المعلّقة قبل الجهوزيّة **تُصَفّ لا تُفقَد**.
   * 🛑 **`ValidateReceipt` لا تتحقّق من شيء**: ٦٢٨ بايتًا سجلٌّ ثم **قفزة ذَيليّة**
     إلى `SubmitReceipt` @`0x508CF9C`.
   * ⭐⭐⭐ **`confirm()` له بابان فقط**: `OnServerSuccess` (§٧.٦)، **و`OnServerError` عند
     `KammelnaError.AlreadyProcessed = 7002` وحدها** (`mov w8,#0x1B5A; cmp; blr` @`0x508D8BC`).
     أيّ خطأ آخر ⇒ **لا `confirm`** ⇒ المعاملة تبقى معلّقة ويُعاد إرسالها في الجلسة القادمة.
   * 🚩 و`OnServerError` **يُهمل وسيط `message` تمامًا** (`x4` لا يُقرأ في الـ272 بايتًا)،
     ويعرض `responseErrorCode.GetFriendlyName()` بدلًا منه.
5. ~~🟡 هل ترتيب `PurchaseProduct` ثم `ShowLoading` في الفرع الافتراضيّ مقصود أم سهو؟~~
   ✅ **حُسم بقدر ما يسمح كود الآلة، في [٠٥ §٢.٤](05-محرّك-IAP-مفكوكًا.md): سهوٌ لا قصد،
   وغير قابل للاستغلال.** الحجّة: `Unity.PurchaseProduct` **غير متزامنة** (تعود فورًا
   والنتيجة تأتي عبر `OnPurchasePending`)، فالفرق أطرٌ قليلة لا ثغرة؛ وكل فروع `BuyProduct`
   الأخرى تنتهي بـ`return` **بلا `ShowLoading` إطلاقًا** ⇒ النافذة ليست جزءًا من العقد،
   بل سطرٌ أُضيف في آخر الدالّة — وهو موضع السهو المعتاد.
   ⚠️ والإغلاق سليم على كل حال: `PopupWindow.DismissMessage()` تُنادى في `OnPurchaseCompleted`
   **و**في `OnPurchaseFailed` @`0x508B594`. **في إعادة البناء: اعرض التحميل أوّلًا ثم ادفع الطلب.**
