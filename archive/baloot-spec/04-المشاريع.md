## 2. تعريف كل مشروع (شروط التكوين) — مقروء حرفيًا من الكود

✅ `[CS: BalootProjectUtility.cs → static BalootProjectUtility()]`
كل عنصر هو `KeyValuePair<BalootProject, ProjectConditions>` و`ProjectConditions` معرّفة في `[CS: ProjectConditions.cs]`:

```csharp
public struct ProjectConditions {
    public ProjectType Type;   // نوع المشروع
    public Rank MaxRank;       // أعلى مرتبة مسموحة
    public Rank MinRank;       // أدنى مرتبة مسموحة
    public int  Size;          // عدد الأوراق
}
```

### 2.1 قائمة `ProjectDefinitions` (بترتيب الأولوية من الأعلى) ✅

| # | المشروع | `ProjectConditions` | الشرح |
|---|---|---|---|
| 1 | `P400` | `(SuitsGroup, MaxRank=ACE, MinRank=ACE, Size=4)` | **أربع إكك** (٤ آسات) |

| 2 | `P100` | `(RankSequence, Max=ACE, Min=SEVEN, Size=5)` | **خمس ورقات متتالية** من نفس النوع |
| 3 | `P100` | `(SuitsGroup, Max=ACE, Min=TEN, Size=4)` | **أربع ورقات من نفس المرتبة** من ١٠ فما فوق (١٠، ولد، بنت، شايب، إكة) |
| 4 | `P50` | `(RankSequence, Max=ACE, Min=SEVEN, Size=4)` | **أربع ورقات متتالية** |
| 5 | `Sira` | `(RankSequence, Max=ACE, Min=SEVEN, Size=3)` | **ثلاث ورقات متتالية** |

> ⚪ تأكيد من نص اللعبة `[LOC: projexts_values_text]`:
> «ترتيب الورق في المشاريع: كل **ثلاث ورقات متتالية سرا**. **أربع ورقات متتالية ٥٠**.
> **خمس ورقات متتالية ١٠٠**. كل **أربع ورقات من النوع نفسه ١٠٠** (ماعدا السبعة والثمانية والتسعة).
> **الأربع أبناط ٤٠٠ في الصن و١٠٠ في الحكم**.»
>
> ⚪ و`[LOC: sarraIs] / [LOC: 50Is] / [LOC: 100Is] / [LOC: 100Is2] / [LOC: 400Is] / [LOC: balootIs]`.

> **لاحظ**: `MinRank = TEN` في مشروع «أربع من نفس المرتبة» يستثني السبعة والثمانية والتسعة بالضبط كما في النص. ✅

### 2.2 قائمة الحكم `HokomProjectDefinitions` ✅

```csharp
// [CS: BalootProjectUtility.cs → <>c.<.cctor>b__6_0]
HokomProjectDefinitions = ProjectDefinitions.Where(pair => pair.Key != BalootProject.P400);
```

**أي أن مشروع ٤٠٠ غير موجود أصلًا في الحكم**؛ الأربع إكك تُلتقط بقاعدة
`(SuitsGroup, ACE..TEN, 4)` فتُحتسب **١٠٠**. ✅ ← وهذا يطابق ⚪ `[LOC: 400Is]`: «مشروع ٤٠٠ أربع اكك **يحسب ١٠٠ في الحكم**».

### 2.3 تسلسل المراتب (ما معنى «متتالية»)

✅ يُحسب داخل `[CS: KammelnaOffline.Baloot.BalootUtils.cs → FindSequenceProject / CheckProjectSira]`
والترتيب المستخدم هو **الترتيب الطبيعي للمرتبة** (7-8-9-10-J-Q-K-A)،
وليس ترتيب القوة. ✅ `[CS: BalootProjectUtility.cs → <ProjectPrecedence>b__4_2]` يقرأ `card.Rank` مباشرة.

> **تنبيه لإعادة البناء**: التسلسل في البلوت يستخدم الترتيب الأبجدي للورق
> (٧ ٨ ٩ ١٠ ولد بنت شايب إكة) وليس ترتيب الأكل. مثال: (ولد، بنت، شايب) = سرا ✅.

## 3. قيم المشاريع

### 3.1 القيمة بالأبناط

✅ `[CS: KammelnaOffline.Baloot.BalootUtils.cs → ProjectAbnat]` — جدول `[BIN: 0x72534F0]`

| المشروع | الأبناط |
|---|---|
| `Sira` | **20** |
| `P50` | **50** |
| `P100` | **100** |
| `P400` | **400** |

### 3.2 التحويل إلى نقاط

✅ `[CS: KammelnaOffline.Baloot.BalootUtils.cs → ProjectValue(project, gameMode)]`
الصيغة الفعلية المفكوكة (مع القيم مضمّنة في ثابت 64-بت `0x0190006400320014`):

```csharp
int raw   = ProjectAbnat(project);                  // 20 / 50 / 100 / 400
int div   = (gameMode == Hokom) ? 10 : 5;
int value = raw / div;
if (project == BalootProject.P400) value >>= 1;     // القسمة على 2
return value;
```

النتيجة المحسوبة ✅:

| المشروع | الأبناط | **في الصن** | **في الحكم** |
|---|---|---|---|
| سرا | 20 | **4 نقاط** | **2 نقطة** |
| ٥٠ | 50 | **10 نقاط** | **5 نقاط** |
| ١٠٠ | 100 | **20 نقطة** | **10 نقاط** |
| ٤٠٠ | 400 | **40 نقطة** | (غير متاح — يُحتسب ١٠٠ ⇒ **10 نقاط**) |
| **بلوت** | — | لا يوجد | **2 نقطة** |

> ⚪ تأكيد `[LOC: Abnat_calc_3]`:
> «**في الصن** اللعب على ٢٦ نقطة، تضاف **٤ نقاط للسرا، ١٠ للخمسين، ٢٠ للمية، ٤٠ للـ٤٠٠**.
> **في الحكم** اللعب على ١٦ نقطة، تضاف **نقطتان للسرا، نقطتان لمشروع البلوت، خمس نقاط للخمسين، عشر نقاط للمية**.»
>
> ✅ تطابق تام بين الصيغة البرمجية ونص اللعبة.

## 4. مشروع البلوت (الشايب والبنت من نوع الحكم)

⚪ `[LOC: balootIs]`: «**مشروع بلوت**: الشايب والبنت في الحكم من ذات الحكم».

| البند | القيمة |
|---|---|
| الشرط | امتلاك `KING` و`QUEEN` من **نوع الحكم** |
| النمط | **الحكم فقط** |
| القيمة | **٢ نقطة** ⚪ `[LOC: Abnat_calc_3]` |
| التعداد | `BalootProjectExtra.Baloot = 6` ✅ |
| الصوت | مقطع `baloot` ✅ |

### ⭐⭐ متى يُعلَن بالضبط — ✅ مُثبَت من كود الآلة

`BalootGameController.OnPlayCard` @`0x5202570`:

```asm
0x520281C sturh wzr, [x19, #0xB5]   ; BalootProjectShown = EkkahProjectShown = false
0x5202820 ldr   w8,  [x19, #0xAC]   ; GameMode
0x5202830 cmp   w8,  #2             ; == Hokom
0x5202834 b.ne  #0x5202A10          ; ⇒ لا بلوت إلا في الحكم
0x520283C ldr   w8,  [x21, #0x10]   ; card.Rank
0x5202840 and   w8,  w8, #0xFFFFFFFE
0x5202844 cmp   w8,  #0xA           ; ⇒ Rank ∈ {QUEEN=10, KING=11}  ⭐ اختبار مضغوط بمسح البت الأدنى
0x5202848 b.ne  #0x52028D8
0x520284C ldr   w8,  [x21, #0x14]   ; card.Suit
0x5202850 ldr   w9,  [x19, #0xB8]   ; TrumpSuit
0x5202854 cmp   w8,  w9
0x5202858 b.ne  #0x52028D8          ; يجب أن تكون من نوع الحكم
0x52028CC ldr   w9,  [x8, #0x30]    ; BalootOfflinePlayer.BalootCounter
0x52028D4 str   w9,  [x8, #0x30]    ; ++
0x5202950 cmp   w8,  #2
0x5202954 b.ne  #0x5202A10          ; ⭐⭐ لا يُنادى إلا عند العدّاد == 2 بالضبط
0x52029B0 bl    #0x5203520          ; PlayingManager.CheckBaloot(playerIndex, BestProjectTeam)
```

✅ **البلوت يُعلَن عند لعب الورقة الثانية من (شايب/بنت الحكم) بالضبط** — عدّاد
`BalootCounter` @`+0x30` على اللاعب، والنداء عند `== 2` حصريًّا.
(هذا هو المُستدعي الوحيد لـ`CheckBaloot`.)

### 🛑 قاعدة لم تكن موثَّقة إطلاقًا

`BalootPlayingManager.CheckBaloot(int playerIndex, int bestProjectTeam)` @`0x5203520` (1,564B):

* جدول المقعد→الفريق `int[4] {1, 2, 1, 2}` @`0x713BC70` ✅ (قرأته بنفسي).
* الشرط: `فريق اللاعب == bestProjectTeam` **و** `p.ProjectCards.Contains(KING of trump)`
  **و** `Contains(QUEEN of trump)`.
* **إذا تحقّق ⇒ سجلّه في `dp` مصفوفة فارغة** (`mov w1, #0` @`0x5203998`).
* وإلّا ⇒ `p.HasBaloot = true` (@`+0x34`) و`controller.BalootProjectShown = true` (@`+0xB5`)،
  وسجلّه `{"baloot"}`.

> ⭐ **القاعدة**: إذا كان شايب وبنت الحكم **كلاهما ضمن مشروع مُعلَن** (سرا/٥٠/١٠٠)
> **فلا يُمنح البلوت منفصلًا** — الورقتان مستهلكتان داخل المشروع.
>
> ⚠️ ملاحظة أمانة: الفرع السالب يضبط `HasBaloot = true` حتى للاعبي الفريق الآخر، لكنه
> غير مؤثّر لأن `CalculateProjects` @`0x5201E74` لا تمرّ إلا على لاعبي `BestProjectTeam`.

**مصدر `ProjectCards`** ✅: `UpdateDeclaredProjectsFirstMove` @`0x5203B3C` (2,104B) —
`player.ProjectCards = declaredProjects.SelectMany(p => p.Cards).ToList()`
(`SelectMany` @`0x5204064` → `ToList` @`0x520406C` → `str x0, [x22, #0x38]` @`0x5204080`).

النتيجة تُكتب في `RoundState["dp"]` كـ`SFSArray` من أربع مصفوفات نصّية.

### 7.1 قاعدة الفريق صاحب المشاريع

✅ `GetBestProjectTeam(dealer, playersCards, gameMode)` — يُرجع **فريقًا واحدًا فقط** يحصل على كل نقاط المشاريع.
🟡 القاعدة (متوافقة مع البلوت القياسي وبنية الدالة):
1. يُقارن **أعلى مشروع** لدى كل فريق بـ `OrderingValue`.
2. الفريق صاحب الأعلى يأخذ **كل مشاريعه**، والفريق الآخر **لا يأخذ شيئًا**.
3. عند التساوي في نوع المشروع، تُرجَّح الأوراق الأعلى مرتبة ثم الأقرب للموزّع (لذلك تُمرَّر `dealer`).

⚪ إحصائية مؤيدة: `[LOC: winWithEnemyHundred_info]` «عدد المرات التي ينجح فيها مشترى اللاعب
والخصم عنده **مية بنط أو أكثر**» — ما يعني أن المشاريع تُحتسب لفريق واحد.

## ⭐ خوارزميات الكشف

هذا الفصل يوثّق **تعريفات** المشاريع وقيمها.
أما **كيف تُكتشف** — النافذة المنزلقة للتسلسل، والتجميع بالرتبة، ومجموعة القوّة التي
تحلّ التنافس بين المشاريع المتداخلة — ففي [١٥ §٤٥](15-تدقيق-ARM64.md).

⭐ **نتيجة حاسمة**: تسلسل المشروع يتبع **ترتيب الرتبة الطبيعي** (`7 8 9 10 J Q K A`)
**لا جدول قوّة الصن**. ولا يوجد في الكود أي مفهوم «تسلسل أطول = مشروع أكبر» —
التسلسل الأطول يُنتج نوافذ متعدّدة متداخلة يُحسم بينها بمجموعة القوّة.
